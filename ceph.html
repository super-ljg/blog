01

为什么要「统一」存储

一个中等规模的技术团队，存储通常长这样：数据库要块设备，于是买了一套 SAN； 训练和分析要共享目录，于是搭了一套 NFS 或 Lustre；备份和静态资源要对象存储，于是又上了一套 S3 兼容系统。

三套系统意味着三份硬件、三套运维、三种扩容方式，而且它们之间不能互相借容量。Ceph 想解决的就是这件事：

一句话理解 Ceph

把一堆普通服务器的本地硬盘，组成一个统一的分布式存储池；这个池子同时提供对象、块、文件三种访问方式，容量和性能随机器数量线性增长，坏盘坏机自动恢复。

它敢这么做的底气，来自三层设计：

  • 底座只有一种东西：对象。块设备是「把对象拼成磁盘」，文件系统是「给对象加上目录」，对象存储是「直接暴露对象」。三种接口共用同一套数据路径。
  • 没有中心元数据服务。数据放在哪，由客户端用一套确定的算法（CRUSH）自己算出来，不需要问一台中心服务器，也不存在「元数据节点挂了全集群停摆」。
  • 把「会坏」写进设计。副本、心跳、peering、backfill 都是常规流程，不是应急预案。

背景：Ceph 起源于 Sage Weil 的博士工作，核心论文是 2006 年的《CRUSH: Controlled, Scalable, Decentralized Placement of Replicated Data》。今天由 Ceph 基金会维护，是 OpenStack、Kubernetes（Rook）、Proxmox 等平台的常见存储后端。

02

一个底座，三张面孔

先记住这张分层图。上面三种颜色是用户能看到的三张脸，下面灰色那一层是真正的存储引擎，叫 RADOS （Reliable Autonomic Distributed Object Store，可靠、自治的分布式对象存储）。

类比

把 RADOS 想成一个巨大的仓库，货物统一装进标准箱子（对象）。块存储是把箱子按顺序拼成一条长走廊；文件系统是在箱子上贴目录标签；对象存储则直接让你按编号取箱子。仓库只有一套，取货窗口有三个。

03

谁在干活：五个守护进程

装过 Ceph 的人都会被一堆进程名绕晕。其实只有五个角色，各自职责非常清楚：

进程职责是不是数据必经之路
MON维护集群地图（谁在、数据怎么分布），用 Paxos 组成仲裁组否，只在启动/变更时查询
OSD一块盘一个进程，真正存数据、做副本、做恢复是，所有 I/O 都落在这里
MGR汇总指标、跑 Dashboard、负载均衡建议否
MDS只有 CephFS 用，管目录树和文件元数据CephFS 的元数据必经
RGW对象网关，把 S3/Swift 请求翻译成 RADOS 操作对象接口必经

这张图里最容易被忽略的两点，恰好是 Ceph 的招牌：

  • MON 不是元数据服务器。它存的是「地图」：哪些 OSD 在、每个 OSD 多重、数据怎么分布。客户端拿到地图后自己算位置，数据面完全不经过 MON。
  • MDS 只服务文件接口。用 RBD 和 RGW 时根本不需要它。这也是为什么 CephFS 常常是最后才上的那块——它引入了一个需要精心扩容的组件。
04

RADOS 的四个名词

后面所有内容都建立在这四个词上，值得多花两分钟：

名词是什么关键点
object 对象带名字的字节块，比如 rbd_data.abc.0000000000000010大小有上限，可以被整体读写、整体校验
pool 存储池对象的逻辑分区，决定副本数、纠删码、PG 数量像「表空间」，不同的池可以有完全不同的策略
PG 归置组一批对象的集合，是复制和恢复的最小单位一个 PG 落在哪几个 OSD 上，由 CRUSH 决定
OSD一块盘上的守护进程，负责落盘、复制、恢复集群里成百上千个，坏了就换，数据自动补

为什么要在「对象」和「OSD」之间插一层 PG？因为如果每个对象单独决定放哪、单独做副本、单独做恢复，几亿个对象的管理开销会直接压垮集群。 把对象打包成 PG（通常一个 PG 装几千到几万个对象），复制、校验、迁移都以 PG 为单位，复杂度立刻降了一个数量级。

类比

对象是书，PG 是书架上一格一格的「书箱」，OSD 是书架。你不会给每本书单独安排位置和备份，而是按箱管理：一箱书整体放到三个书架上，箱子丢了就整箱补。

05

CRUSH：不用查表的寻址

传统分布式存储靠一张「对象 → 节点」的映射表，这张表存在元数据服务器上。对象一多，表就巨大；节点一变，表就要重算；元数据服务器还成了单点。

Ceph 的做法是：不存表，存算法。位置由两步计算得到，任何客户端、任何 OSD 算出来都一样： 

第一步：PG = hash(对象名) & (pg_num - 1)
        → 对象稳定地落进某个 PG（pg_num 是 2 的幂）

第二步：OSD 列表 = CRUSH(pgid, 集群地图, 规则)
        → 得到 [osd.12, osd.7, osd.31]，分属三台不同主机

「故障域」是 CRUSH 的关键词

CRUSH 地图不是一张平铺的 OSD 列表，而是一棵树： root → rack → host → osd。规则里会写明「三个副本必须落在不同 host」， 于是算法在选副本时会跳过同一台机器。这样一台机器整机断电，最多只丢一份副本。

再进一步，如果你的机架共用一路电，就该把规则写成「不同 rack」。故障域定多细，取决于你怕什么—— 怕单盘坏、怕整机坏、还是怕整个机架掉电。

常见误解

CRUSH 不是一致性哈希。一致性哈希只解决「节点增减时少搬数据」，不解决「副本必须分散在不同故障域」；CRUSH 用带权重的伪随机选择同时解决这两件事，代价是算法和地图都更复杂。

06

一次写，怎么落到三块盘上

PG 选出的那组 OSD 里，有一个是 primary（主），其余是副本。 客户端只跟 primary 说话，primary 负责把写并行发给所有副本，全部确认后才回复客户端。

这里有个设计取舍值得说清：并行写让延迟取决于「最慢的那个副本」，而不是累加； 但主 OSD 要暂存所有未完成的写，内存和网络压力集中在一台机器上。这也是为什么 Ceph 的 OSD 需要不错的 CPU 和网络，而不是只堆硬盘。

至于落盘，现代 Ceph 默认用 BlueStore：直接操作裸设备，数据块自己管，对象元数据放在 RocksDB 里。 相比早期的 FileStore（数据先写本地文件系统再落盘），它少了一层间接，也避免了文件系统的双重缓存。

07

坏了怎么办：从 degraded 到 clean

一块盘掉了，PG 立刻进入 degraded（降级）状态：副本数不足，但数据还在，读写继续。 同时 MON 会更新 OSD 地图，把这块盘标记为 down，并把新的地图推给所有客户端和 OSD。

接着，CRUSH 会为受影响的 PG 重新选一个 OSD 来补位。新 OSD 需要从现有副本把数据拷过来，这个过程叫 backfill。 在补完之前，这个 PG 处于 active+undersized+degraded；补完之后回到 active+clean。

PG 的状态，就是集群的健康报告

跑 ceph -s 时看到的那一行，其实是所有 PG 状态的汇总。常见的几个：

状态含义要不要紧张
active+clean副本齐全，读写正常健康
degraded副本数不足，但还能读写要关注，等它自愈
undersized实际副本数少于配置值同上，通常一起出现
peering副本之间正在协商谁的数据最新短暂正常
backfilling正在把数据拷给新 OSD正常，但会吃带宽
remappedPG 暂时落在非理想位置恢复期常见
staleMON 收不到这个 PG 主 OSD 的汇报要查，可能是网络分区
inconsistentscrub 发现副本内容不一致要查，通常意味着静默损坏

还有两个后台动作要区分：scrub 只比对元数据和校验和，很快； deep-scrub 会读出全部数据逐块校验，很慢但能发现「盘说写成功、实际数据坏了」的静默错误。 生产环境一般错峰跑，别和备份抢带宽。

08

扩容：为什么数据会自己搬家

加机器是 Ceph 最日常的操作，也是最容易让人紧张的：ceph osd crush add 一执行，监控上立刻出现一片 backfilling。 这不是故障，是设计使然——新盘加入后权重变了，一部分 PG 需要搬到新位置去，让数据重新均匀。

一个能算出来的数

从 n 个等权重的 OSD 扩到 n+1 个，大约有 1/(n+1) 的数据需要移动。100 块盘加 1 块，只搬 1%；10 块盘加 1 块，要搬 9%。集群越大，扩容越平滑——这也是为什么小集群扩容反而更疼。

下面这几条命令，基本覆盖了扩容时的全部操作：

# 看谁在迁、迁了多少
ceph -s
ceph pg stat

# 限制恢复速度，别把业务带宽吃光
ceph config set osd osd_max_backfills 1
ceph config set osd osd_recovery_max_active 3
ceph config set osd osd_recovery_sleep 0.1

# 维护窗口：先停数据迁移，再动硬件
ceph osd set noout
ceph osd set norecover
顺序很重要

维护前先 noout，是避免 MON 把这台机器判死、触发一轮没必要的迁移；维护完记得 unset，否则它会一直「假装健康」，等你发现时已经少了一份副本。

09

三张脸，各自的门道

块存储 RBD：把对象拼成一块盘

一个 RBD 镜像（image）在 RADOS 里就是一堆对象，按固定大小切开、编号。挂载到主机上就是 /dev/rbd0， 可以被格式化成 ext4/XFS，也可以直接给数据库用。

  • 精简置备：声明 1TB，实际只占用写过的部分，创建瞬间完成。
  • 快照与克隆：快照是写时复制，克隆可以在几秒内派生出一个新卷，适合批量开环境。
  • 不适合：多个客户端同时读写同一块未加集群文件系统的盘。RBD 不是共享盘，要做共享请上 CephFS 或 GFS2。

文件系统 CephFS：多一个 MDS

CephFS 把目录树拆成元数据（放元数据池）和数据（放数据池）。MDS 负责目录、权限、文件锁， 并用动态子树分区把目录树切成几段分给多个 MDS，热点目录可以单独迁到空闲的 MDS 上。

它的短板也很清楚：元数据操作要经过 MDS，海量小文件、频繁 stat 的场景会成为瓶颈； MDS 的扩容与排障，比 OSD 麻烦得多。纯大文件顺序读写反而很轻松。

对象存储 RGW：S3 的门面

RGW 是无状态网关，把 HTTP 请求翻译成 RADOS 对象操作。桶索引本身也是对象（分片存放）， 所以「列桶」这类操作在超大桶上会比读写慢，这也是所有对象存储的通病。

多站点复制（multisite）是异步的：两个站点各自可写，最终一致。别把它当同步容灾。

副本还是纠删码？

PG 的冗余方式由 pool 决定。副本简单、可任意覆盖写、恢复快；纠删码省空间，但写要「读旧数据、算校验、再写」，小随机写会被放大。

10

运维真正会疼的地方

Ceph 的架构很优雅，但它的运维曲线不温柔。下面几个坑，几乎每个生产集群都会踩：

坑现象怎么防
PG 数不合理每 OSD 的 PG 过少 → 分布不均；过多 → 内存和 peering 开销爆炸按「每 OSD 100–200 个 PG」估算，开 pg_autoscaler
集群快满到 nearfull 开始告警，到 full 直接拒绝写，且无法自愈留 20% 余量，监控 full ratio，别等 95%
时钟漂移MON 之间时间不同步，仲裁异常所有节点跑 NTP/chrony，这是硬要求
恢复风暴换一块盘引发全集群 backfill，业务延迟飙升限制 backfill/recovery 并发与带宽，错峰
小对象太多RGW 列桶慢、RBD 元数据压力大合并小文件，或换更适合的系统
误操作删池数据瞬间不可恢复开 mon_allow_pool_delete=false，快照与异地备份

经验公式是「每块 OSD 承载 100 个左右的 PG」，再按副本数折算成池的 pg_num。改下面的数字看看：

建议单个池的 pg_num ≈ 1024 已向上取到 2 的幂；若集群有多个池，请把这些 PG 在各池之间分摊，而不是每个池都用这个数。

11

一页总结

如果只记六句话

  1. 一个底座，三种接口。对象、块、文件都落在 RADOS 上，扩容一次三头受益。
  2. 没有中心元数据。位置靠 CRUSH 算出来，客户端拿着地图直接找 OSD，MON 不碰数据。
  3. PG 是管理单位。对象打包成 PG，复制、校验、迁移、恢复都以 PG 为单位。
  4. 写靠主副本。主 OSD 并行写所有副本，全确认才应答；min_size 决定降级时的底线。
  5. 故障是常态。降级、peering、backfill 都是常规流程，关键是别让恢复拖垮业务。
  6. 扩容即重平衡。加盘会搬约 1/(n+1) 的数据，集群越大越平滑；记得限速。

如果你读过本站的 3FS 那篇，会发现两个系统在同一个问题上给出了相反答案：

维度Ceph3FS
元数据无中心，CRUSH 计算位置无状态服务 + FoundationDB
冗余副本或纠删码，可混用链式复制（CRAQ），强一致
接口对象 / 块 / 文件三套POSIX 文件 + 原生零拷贝 API
定位通用统一存储，能跑十年AI 训练/推理，为吞吐极致优化
代价运维复杂，小文件与元数据偏弱依赖 RDMA，小文件与通用性让位

Ceph 的厉害之处不在于某个单点的性能，而在于它用一套没有中心、可以自己算、坏了自己补的模型， 撑住了「对象、块、文件」三种完全不同的用法，并且能在同一批硬件上跑十年。理解了 CRUSH 和 PG，这套系统就不再神秘了。
