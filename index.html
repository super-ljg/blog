01

为什么要自研一个文件系统

先看训练集群里真实发生的三件事，它们对存储的要求几乎互相矛盾：

  • 喂数据（Dataloader）：几千张卡各自随机抽取训练样本，读的大小从几十 KB 到几 MB 不等，而且样本在文件里通常不对齐。需要的是海量随机小读。
  • 存 checkpoint：每隔一段时间，所有卡同时把模型权重刷出去，瞬间产生几十 TB 的写入。需要的是极高带宽的顺序写。
  • 推理 KVCache：把历史 token 的 KV 向量放到外部存储，下次直接复用，省掉重复计算。需要的是大容量 + 高吞吐 + 可回收。

现成方案都不太合适。对象存储吞吐够，但没有真正的目录语义：把目录整体 rename 是原子的、递归删除整个目录、 软链接做数据集快照——这些在对象存储上要么做不到，要么得靠应用层凑。传统网络文件系统（NFS 类）单点瓶颈明显， 带宽随节点数上不去。而每台机器挂本地盘，又变成一个个数据孤岛，别的机器读不到。

3FS 的三条设计目标，正好对应上面三个痛点：

三句话记住 3FS

① 位置无关：应用不需要知道数据在哪块盘、哪台机器上，像访问本地文件一样访问整个集群的存储。

② 强一致：多个客户端并发读写，看到的结果和单机文件系统一样好推理，不用在应用里处理「可能读到旧数据」。

③ 文件接口：POSIX 风格的文件与目录，现有代码几乎不用改就能接进来。

名字里的 Fire-Flyer 是 DeepSeek 内部计算集群的代号。它不是一个通用型存储产品， 而是为「大文件、高吞吐、读多写少、集群内网」这个非常具体的场景，做了大量针对性取舍——这点后面会反复出现。

02

全景：四个角色，一张网

3FS 只有四种进程，全部连在同一张 RDMA 网络（InfiniBand 或 RoCE）上。可以用一个图书馆来类比：

  • 客户端（Client）＝ 读者。它拿着借书证（文件描述符）来借书，自己不藏书。
  • 元数据服务（Meta Service）＝ 前台目录柜。它只管「哪本书在哪个区」，不碰书的内容。
  • 存储服务（Storage Service）＝ 书架。书（数据）真正放在它管理的 SSD 上。
  • 集群管理器（Cluster Manager）＝ 馆长。谁在上班、哪个书架坏了、该怎么重新分配，都归它管。

注意图里那条虚线：元数据和存储服务都持续向集群管理器发心跳。心跳不是「报个平安」那么简单， 它本质上是在续租约——这一点在第 7 节讲故障时会成为关键。

组件一句话职责有没有状态
客户端把应用的 open/read/write 翻译成对存储服务的请求只缓存布局信息
元数据服务实现文件系统语义，把目录操作翻译成 KV 事务无状态（状态在 FDB）
存储服务管理本地 SSD，对外提供 chunk 读写有状态（数据 + chunk 元数据）
集群管理器成员管理、故障判定、维护并广播复制链表有状态（存 FDB，多副本选主）
03

数据怎么摆：文件 → chunk → 链

3FS 不在存储节点上维护一棵「完整的目录树」。它先把文件切成等长的块，再用「复制链」把这些块分散到很多块盘上。 这里有四个必须分清的词，是后面所有讨论的地基：

概念是什么类比
chunk文件按固定大小切出来的块，chunk ID = inode ID + 块序号把一本厚书拆成若干册
target一块 SSD 上的一块逻辑存储单元，是复制的最小单位书架上的一个格子
chain若干 target 按顺序排成的一条复制链（通常 3 副本），有版本号同一本书放在 3 个格子里，标好先后
chain table一组链的集合，决定数据的整体放置策略整个书库的分区方案

为什么要绕这么一圈？因为如果一个大文件整块放在一台机器上，那台机器的网卡就是瓶颈，别的机器的带宽全闲着。 切成 chunk 再条带化（stripe）到多条链上，读一个大文件时，几百块 SSD 和几百张网卡同时在干活， 聚合带宽才可能到 TB/s 级别。

建文件时发生了什么

创建文件时，元数据服务按 stripe 大小从指定的 chain table 里轮询挑一段连续的链，再生成一个随机种子打乱顺序， 把「选了哪一段链 + 种子 + chunk 大小」写进 inode。之后客户端只要读一次 inode，就能在本地算出每个 chunk 的位置。

类比

像快递分拣：包裹（chunk）按规则轮流扔进不同的传送带（chain），传送带上三个站点（target）各存一份。收件人只要知道「我的包裹走哪条传送带」，就能直接去取，不用每次问总台。

chain table 还可以有多张，比如一张给离线批处理、一张给在线服务，用的节点和 SSD 互不重叠，避免大作业把在线业务拖垮。 这个设计很朴素，但在生产环境里非常实用。

04

强一致：写走一条线，读能随便挑

一份数据存 3 个副本，马上冒出一个问题：写的时候 3 份都要改，怎么保证别人读不到「改了一半」的状态？ 3FS 用的是 CRAQ（Chain Replication with Apportioned Queries，带查询分摊的链式复制）。

它的核心约定只有两条：

  • 写，只发给链头，然后沿链一站一站往下传，全部确认后才算成功（write-all）。
  • 读，可以发给链上任意一个副本，把读流量摊到三块盘上（read-any）。

写路径：像接力赛，最后一棒才交卷

这套流程里有个容易被忽略的细节：请求里带的是「整块 chunk」而不是「改哪几个字节」。 原因在于故障恢复——节点重新上线时，前驱可以简单地用「整块覆盖写」把数据灌给它，不用回放复杂的增量日志。 代价是写入要先把旧 chunk 读出来、改完再写回去（copy-on-write），换来的是恢复逻辑极其简单可靠。

为什么写要串行

如果两个客户端同时改同一个 chunk，让三份副本各自按不同顺序应用，就会出现三份数据不一致。把并发收敛到链头一把锁上，顺序就只有一个版本，其余节点只是忠实地按顺序执行。

读路径：三份副本都能干活

如果只能从链头读，那另外两份副本就纯属浪费带宽了。CRAQ 允许客户端从任意一个副本读， 这让读吞吐能随副本数线性增长——对「读远多于写」的 AI 训练负载，这是最划算的一笔交易。

一句话理解 CRAQ

写：只许从总店进货，一件件往下游门店送，最后一家签收了才算数。读：哪家店近去哪家买；如果店员正在理货，就等一下，或者拿刚上架还没盖章的那件（宽松读）。

这里能看出 3FS 的取舍非常明确：牺牲写延迟，换读吞吐。写要逐跳传播，延迟比「三副本并行写」高； 但 AI 集群里读的量级远大于写，而且 checkpoint 这类写是超大块顺序写，对单次延迟不敏感。取舍是对着负载算过的。

05

元数据：无状态前台 + 一个靠谱的账本

「哪个文件有哪些 chunk、在哪些链上、权限是多少、目录里有什么」——这些叫元数据。 传统分布式文件系统里，元数据服务常常是最难搞的部分：它是全局单点，热点目录能把它压垮，重启一次全集群卡住。

3FS 的做法很干脆：元数据服务自己不存任何东西，所有状态写进 FoundationDB（一个支持可串行化事务的分布式 KV）。 于是元数据服务变成一堆完全对等的无状态进程，客户端连哪个都行，挂一个就换一个， 升级重启对上层几乎无感。

FDB 的事务会记录读写键集做冲突检测，冲突了元数据服务自动重试。于是几个经典难题被「下沉」掉了： 多客户端同时改一个目录、rename 时检测目录成环、并发创建同名文件——都由事务模型兜底，不用自己写一套分布式锁。

几个为规模做的「小动作」

这些细节不起眼，但正是它们让系统在几千个客户端下还能跑：

  • 只读 fd 不跟踪。训练任务一启动就打开几十万个文件，如果每个 fd 都在元数据里登记，FDB 会被压垮。反正训练不依赖「删除已打开文件要延迟」这个语义，干脆不记。
  • 写 fd 记 session。写模式下打开的文件会登记会话，删除要等所有 fd 关闭，避免并发写产生永远回收不了的垃圾块；客户端掉线后，元数据服务定期清理它的会话。
  • 文件长度允许暂时不准。活跃写入时，客户端每 5 秒上报一次最大写位置，取个近似值；到 close/fsync 时才去问存储服务「最后一个 chunk 到底多长」，拿到精确值。
  • stripe 用 200，但只查用到的那几条链。生产环境 stripe 很大，小文件其实只落在少数链上。inode 里存一个「可能用到的链数」提示，初始 16，每次写更多链就翻倍，避免为了算长度把 200 条链全问一遍。
  • 长度更新按 inode 哈希分摊。多个元数据服务同时更新同一个文件的长度会撞事务，用 inode ID 做一致性哈希，把这类任务分派到不同进程。
代价

元数据要经过「元数据服务 → FDB → 元数据服务」两跳，小文件密集或海量 stat 的场景延迟不如专用 MDS。这是 3FS 主动接受的结果：它面向的是大文件、高吞吐，不是海量小文件。

06

客户端：一条兼容路，一条性能路

文件系统再好，应用接不进来也白搭。3FS 提供了两种客户端，对应两种心态：先把业务跑起来，和把最后一点性能榨出来。

FUSE 客户端：开箱即用，但有天花板

FUSE 让用户态进程实现一个文件系统，应用完全感知不到差别——ls、open、read 都照常。 门槛极低，但代价藏在两处：

  • 两次内存拷贝。用户态守护进程读不到应用的内存，数据必须先从内核拷到守护进程，再拷回去。带宽白白烧在内存总线上。
  • 一把自旋锁。请求要经过内核里一个共享队列，队列由自旋锁保护。并发一高就全在抢锁，加线程没用。官方实测大约 每秒 40 万次 4KiB 读就到顶了，perf 显示 CPU 大量耗在内核自旋锁上。

另外 Linux 5.x 的 FUSE 不支持同一文件并发写，应用只能靠「同时写多个文件」来堆吞吐——这对 checkpoint 场景恰好可行。

原生客户端：借 io_uring 的思路做零拷贝

理想方案是写内核模块，但内核模块难开发、难调试，出问题可能直接死机，升级还得停掉所有使用该文件系统的进程。 3FS 选择了折中：把原生客户端放进 FUSE 守护进程里。元数据操作（open/close/stat）仍走 FUSE， 保证语义和 POSIX 一致；数据 I/O 则走一套共享内存 + 环形队列的 API。

Iov 是一大块应用和客户端共享的内存，提前注册给 RDMA 网卡，所以网卡可以直接往里写；Ior 是一个小环形队列， 用法类似 io_uring：应用把请求塞进环里，客户端批量取走、批量发出，把「小读请求」的 RPC 开销摊薄。 多线程应用最好每个线程一个环，共享一个环反而要加同步。

怎么选

数据准备、跑批、已有代码不想改 → FUSE 客户端。
训练 dataloader、推理 KVCache 这类对 IOPS 和延迟敏感、愿意改几行代码的 → 原生客户端。

07

故障不是意外，是日常

几千块 SSD、几百台机器，每时每刻都有东西在坏。3FS 的设计前提是：坏盘、宕机、网络分区都会发生， 系统要在这些情况下继续提供接近满血的吞吐，而不是「先降级跑着，等运维换盘」。

第一道防线：心跳即租约

存储和元数据服务持续向主集群管理器上报。超过 T 秒（默认 60s）没消息，管理器判定它失联； 反过来，服务如果超过 T/2 秒联系不上管理器，就主动退出。

后半句很关键：它防的是「脑裂」。网络一断，某个服务可能还活着，但已经收不到最新拓扑了； 如果它继续对外服务，客户端会拿到过期信息写出脏数据。宁可自杀，也不当僵尸。

第二道防线：target 状态机

每个 target 有一个公开状态，随链信息一起广播给所有客户端：

状态能读能写含义
serving✓✓活着，正常服务
syncing✗✓活着，正在从上游同步数据
waiting✗✗活着，但还没开始恢复
lastsrv✗✗已宕机，且曾是链上最后一个在服务的节点
offline✗✗宕机或介质故障

节点被标 offline 后会被移到链尾，链版本号 +1，新拓扑广播出去。 挪到链尾而不是直接踢掉，是为了让写流程还能找到一个「兜底的尾巴」，不至于整条链停摆。

第三道防线：恢复时别把邻居压死

这是我觉得 3FS 最见功力的一处。假设 3 副本的链是 A-B-C，A 的 SSD 挂了，读请求自然落到 B 和 C 身上。 问题来了：如果拓扑是「A 只和 B、C 配对」，那 B、C 要各自多扛 A 的一半流量，瞬间翻倍，直接成为新瓶颈。 而换盘、同步数据可能要几个小时——这几个小时里整个集群的读带宽就被拖垮了。

朴素布局：A 只和 B、C 配对

A 一挂，B、C 各多扛 100% 流量
链1A1B1 +100%C1 +100%
链2A2B2 +100%C2 +100%
链3A3B3 +100%C3 +100%
链4A4B4 +100%C4 +100%
链5A5B5 +100%C5 +100%

B、C 被瞬间打满，集群读吞吐掉一大截，直到新盘同步完。

均衡布局：A 和每块 SSD 都配对

A 一挂，其余 5 块各多扛 20%
链1A1B2 +20%E1
链2A2C1 +20%F1
链3A3D2 +20%B3
链4A4E2 +20%C3
链5A5F2 +20%D3

每块盘只多担一点点，恢复期间仍接近满速。这是用整数规划求解的「平衡不完全区组设计」。

为了让「故障中仍可用」成为一等目标，3FS 把链的构造当成了一个组合数学问题： 让每块 SSD 在链里尽量和所有其他 SSD 都搭档过，这样任何一块挂掉，压力都能被均摊。 这已经不是「实现一个文件系统」的层面了，是拿运筹学在做工程。

数据怎么补回来

节点重新上线后，它会先把自己所有 target 都标成 offline，确保走完恢复流程，然后才开始收心跳。恢复过程与正常读写重叠进行，不阻塞业务：

  • 前驱向它发 dump-chunkmeta，它把本地所有 chunk 的 ID、链版本、committed/pending 版本号回给对方。
  • 前驱对比两份 chunk 元数据，决定哪些该传、哪些该删。
  • 需要补的 chunk，逐个加锁、读出「链版本 + 提交版本 + 完整数据」，以整块覆盖写推过去。
  • 全部推完发 sync-done，它把本地状态置为 up-to-date，重新开始对外读服务。

判断规则也很克制：本地有远端没有 → 补；远端有本地没有 → 删；本地链版本更新 → 补； 版本相同但提交号对不上 → 补；其余情况视为「一致」或「正在被写」，不动。

08

跑分，以及它不适合做什么

官方 README 给了三组数字，都是真实集群、带背景流量跑出来的：

6.6TiB/s
180 个存储节点、500+ 客户端聚合读吞吐，且训练任务仍在跑
3.66TiB/min
GraySort：110.5 TiB 数据、8192 分区，30 分 14 秒排完
40GiB/s
推理 KVCache 客户端读峰值，同时还在做垃圾回收

测试条件：单节点 2×200Gbps InfiniBand、16 块 14TiB NVMe；GraySort 用 25 个存储节点 + 50 个计算节点。这些是特定硬件与负载下的数字，不能直接和别的系统横向比。

它明确放弃的东西

理解一个系统，看它不做什么比看它做什么更有信息量：

场景3FS 的表现原因
海量小文件、频繁 stat不擅长元数据要过 FDB 两跳，且无专用 MDS 缓存层
写多读少不划算CRAQ 写要逐跳传播，延迟高于并行三写
需要完整 POSIX 语义部分缺失文件锁、xattr 等未支持
跨地域 / 公网访问不适用假设集群内 RDMA 网络，低延迟高带宽
没有 RDMA 的环境部署困难设计处处假设 RDMA，普通以太网发挥不出优势
值得记住的一个判断

3FS 在生产环境里端到端不做缓存。在「全闪存 + RDMA」的时代，中间再加一层 DRAM 缓存，可能不但省不了时间，反而变成新的瓶颈和故障点。数据从 NVMe 直接经网卡送到客户端内存——前提是你的网络足够快。这是一个非常依赖硬件前提的赌注，也是一次很清醒的取舍。

如果只记六句话

  1. 控制面与数据面分离。元数据走「无状态服务 + FDB」，数据走「客户端直连存储」，两条路互不拖累。
  2. 位置无关。文件切成 chunk 条带化到很多链上，应用不需要关心数据在哪，聚合带宽才能线性增长。
  3. 读写不对称优化。写收敛到链头串行、逐跳提交换取强一致；读摊到所有副本，换满带宽。因为 AI 负载读远多于写。
  4. 状态放在最靠谱的地方。文件语义、目录并发、rename 成环这些难题，全都下沉给 FoundationDB 的事务模型。
  5. 把故障当常态设计。心跳即租约、失联就自杀防脑裂、链布局用组合设计保证「坏一块盘」时流量均摊。
  6. 用成熟接口降低迁移成本。POSIX 文件语义 + FUSE 客户端让存量代码零改动；想更快再上零拷贝原生 API。

回过头看，3FS 并没有什么玄乎的黑科技。它的厉害之处在于：每一个设计选择都指向同一个目标—— 让几千张 GPU 同时、稳定、可预测地从一堆 SSD 上取数据。为此它可以接受写延迟高一点、小文件慢一点、部署门槛高一点。

这也是读大型开源系统最有意思的地方：你看到的不是一堆技术的堆砌，而是一连串有代价的取舍。 把代价看清楚，比记住架构图更有用。
